| R12 | Generation continues in-app when leaving a conversation (autoDispose keepAlive) and partials persist incrementally (a cold reader after an OS kill sees them) — all unit-verified. NOT yet handled: (a) TRUE background execution when the app is MINIMISED — Android suspends the inference isolate, so a turn pauses and only resumes on foreground (or is lost if the OS kills the process); finishing while backgrounded needs a short foreground service like the download one (deferred: new native surface, unsafe to land without on-device testing). (b) Reconnect for a BRAND-NEW conversation: the thread is family-keyed by ChatRouteArgs, so re-entering a still-generating draft via `/chat/:realId` builds a fresh controller keyed by the real id and shows the frozen partial until the (still-alive, still-generating) draft-keyed controller finalizes to the DB — delayed visibility, not data loss. Existing-conversation reconnect (same key) works and is tested. | MEDIUM | Foreground-service background inference + reactive draft-orphan reconnect are follow-up work; verify on-device via Firebase App Distribution (folds into R1/R9) |
| R13 | Context-shift (`shiftPolicy: auto`, loop/perf-kv-reuse) only protects the GENERATION loop, not prefill: `Generator._prefill()` at the pinned llama_cpp_dart commit has no shift-awareness, so a turn whose cumulative history + new content already exceeds `n_ctx` BEFORE any token is generated still fails with a typed `EngineDecodeFailure` (same as before this change — verified unchanged by `engine_hostile_native_test.dart`'s "decode overflow" case, which still passes). Only a single reply that grows long enough to fill the *remaining* room mid-generation is now auto-trimmed (system prompt preserved via a best-effort `nKeep`, computed by rendering the system turn alone — a template-dependent approximation, not byte-exact). | MEDIUM | Real prefill-time overflow protection needs either a client-side history-truncation policy before calling `generate()`, or a future engine-pin bump that adds shift-awareness to `Generator._prefill`. Verified/tracked on macOS CPU only in this loop — Android/iOS on-device long-chat behavior needs a real device pass (folds into R1/R9). |
| R14 | Prefix-KV reuse (loop/perf-kv-reuse, the main win) and `flashAttn=on + kvCacheQuant=q8_0` were both proven on the real engine (real SmolLM2-135M, macOS/Metal+CPU) in this environment only: prefix reuse measured cold=118 vs warm=17 decoded prompt tokens over a 4-turn conversation (`engine_smoke_test.dart`); q8_0 KV load+generate measured to actually halve KV buffer size (`K/V (q8_0): 2.99 MiB` vs `f16: 5.62 MiB` at the same 512-token context) and complete generation successfully. Both rely on tokenization/KV-cache primitives that are backend-generic, but neither has been exercised on Android (Hexagon/CPU) or iOS (Metal) hardware — the standard "needs on-device verification" gap this project already tracks for every native path. | MEDIUM | Needs an on-device pass via Firebase App Distribution (folds into R1/R9); if it regresses there, the two real-engine tests above (`prefix reuse: ...`, `flashAttn=on + kvCacheQuant=q8_0 ...`) are where to reproduce it first. |
