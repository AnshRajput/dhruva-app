## A. Privacy / "nothing leaves the phone except to the user's own provider"

1. **BLOCKER — Android Auto Backup will copy the mail/notification database to Google Drive.** `AndroidManifest.xml` sets no `android:allowBackup`, `fullBackupContent` or `dataExtractionRules`, so the default (backup on) applies. Once the Drift DB holds mail bodies, contacts and notification text (spec §3), that data is uploaded to the user's Google account backup and transferred on device migration. Gmail is the user's own provider, but backup is not the connector, not shown in the ledger, and not consented. iOS equivalent: DB in Documents is included in iCloud backup. Spec and premortem never mention it. Fix: `allowBackup=false` (or `dataExtractionRules` excluding the connector DB and notification store), `isExcludedFromBackup` on iOS, add to §7 security review and premortem #5. Note this also cuts against the cloud-backup stance parked as G9.
2. **MAJOR — Premortem #5 / brief say "network only to the user's own provider" and ledger header says "0 bytes sent to any Dhruva server".** Existing network use also includes Hugging Face downloads and API, AI news fetch (matrix #42), and Shorebird update checks (`shorebird_code_push`, privacy.md lines 18-20). The claim is false as written and the "0 bytes" header is a static string, not a measurement. Fix: ledger also records HF / Shorebird calls, header reads what is true ("Your mail goes only between this phone and Google"), update privacy.md ("Network use is narrow" paragraph, and the architecture claim that network is confined to HF code under `data/`).
3. **MAJOR — User-initiated exports now leak private content with no warning.** Matrix #13/#14 (export / share chat), #18 (Report a reply, optionally email developer) and Settings crash reports (share/email) were designed when content was only chat. After grounding, replies and chats contain mail excerpts, contact names and file text. Spec never revisits these. Fix: warn at export/share/report when a chat has Sources; report sheet strips grounded excerpts by default; crash logs must never include item bodies or titles (add a test).
4. **MAJOR — Premortem #5 says "no new SDKs".** Spec adds `google_sign_in` (Play Services / GoogleSignIn pod), `googleapis`, `flutter_secure_storage`, `device_calendar_plus`, `flutter_contacts`, a WorkManager plugin and probably `home_widget`. Fix: say "no analytics/ads SDKs; N new plugins, listed" and require per-plugin manifest/permission diff review; update the Play Data safety and Apple privacy manifest answers (`ios/Runner/PrivacyInfo.xcprivacy` exists and will need new accessed-API / data entries).
5. **MAJOR — Plaintext local store with no app lock, widget and tile exposure.** Mail subjects, notification text (which on Android includes message previews from banking and chat apps, only OTPs are redacted by Android 15) and the brief sit in unencrypted SQLite and are shown in the app switcher. The home widget (in-flight feature, spec never describes its content) would show the brief on a home screen / tablet lock screen; the Quick Settings tile launches without unlock. Not in premortem. Fix: decide widget content (events only, no mail text, by default), tile uses unlock-and-run, `FLAG_SECURE` / privacy blur in recents as a setting, notification digest default = opt-in per app (not "all apps minus excluded"), optional app lock on the roadmap.
6. **MAJOR — Indirect prompt injection from mail / notifications / files.** Untrusted text goes into the model ("Draft reply", "Add to calendar" extraction, Ask grounding, brief). The spec has no trust boundary note; matrix #52 `safety_guard.dart` is not mentioned. Impact is limited because nothing sends without a tap, but a crafted mail can steer a draft the user sends, produce a bogus calendar event, or put a link into the brief. Fix: treat item text as data (delimiters, "ignore instructions in the text" is not sufficient), never auto-open links from model output, confirm sheet shows extracted fields, add to premortem and §7.

## B. Factual errors and unverified claims

7. **MAJOR — Gmail scope classes are never stated, and the verification effort is understated.** `gmail.readonly` and `gmail.compose` are both RESTRICTED (spec §3 lists them without class). Only `gmail.send` is sensitive (brief parks it correctly but the reader cannot tell why it differs). Restricted verification needs the app homepage/privacy policy on a verified domain, scope justification, Limited Use disclosure, and a demo video; brief says "about 10 days" (unverified, restricted reviews commonly run longer and repeat on rejection). Fix: label scopes, drop `gmail.compose` for 0.7c if "Open in Gmail / Copy" is enough (one restricted scope instead of two; the draft-saving write is also the only mailbox write), and add the "Google's reviewer disagrees that on-device data is exempt from CASA" case to premortem #2 with a cost/time estimate. The CASA statement itself ("only if data is stored or transmitted on servers") is correct; add that it depends on never syncing mail anywhere, which links to finding 1.
8. **MAJOR — Token storage design does not match `google_sign_in` 7.x.** Spec: "Tokens only in the OS keystore (`flutter_secure_storage`)". In 7.x authentication and authorization are split; `authorizationClient` returns short-lived access tokens, Play Services (Android) / GoogleSignIn (iOS) own the grant, and there is no refresh token for the app to store (unverified in detail, check the package changelog). So `flutter_secure_storage` may be unnecessary, and a WorkManager background isolate may not be able to get a token silently. Also Android 7.x needs a `serverClientId` (a web OAuth client, not a server) (unverified). Fix: prototype silent token fetch from a background isolate before committing to the 6 h Gmail sync; fall back to foreground-only sync.
9. **MAJOR — Premortem #9 claims "deep links (`/chat/:id`) still work".** The manifest has no `VIEW` intent filter; `/chat/:id` is an internal go_router path only. Existing external entry points are the `SEND` filter, `PROCESS_TEXT` alias and two launcher shortcuts. Fix: restate as "internal routes keep their paths" and list the external entry points that must keep working (see finding 13).
10. **MAJOR — FTS5 plan ignores the codebase's own recorded decision.** `chat_repository.dart:106-122` documents that Drift 2.34.2 has no `Fts5Table` DSL, the schema is Dart-table-only, and FTS5 was rejected because it needs hand-written `CREATE VIRTUAL TABLE` DDL plus sync triggers ("real migration risk"). Spec §3 introduces `items_fts` and `bm25()` in a v7 migration without acknowledging this. Fix: state the DDL/trigger approach, confirm `sqlite3_flutter_libs` ships FTS5 on both platforms, and add an FTS migration test on a v5 fixture (premortem #6 only tests table adds).
11. **MAJOR — Schema numbering depends on an unmerged PR.** This tree is v5; spec says "after doc-chat's v6 → v7", premortem says "v5→v7", §7 says "v5→v6→v7". Phasing puts doc-chat in 0.7a and connectors in 0.7b, so v7 may ship a release later (fine) but the numbers will collide if the three other in-flight PRs (speed test, heat guard, tile/widget) also touch the DB. Fix: reserve schema numbers per PR in the spec, and say what happens if doc-chat slips.
12. **MINOR — Walk counts are wrong.** brief.md and audit.md §5 "Count" say 7 leave / 7 guess / 5 retype / 6 none. Counting the tags in steps 1-18: 5 leave (steps 2,4,6,9,17), 9 guess (1,3,7,8,10,11,13,14,17), 4 retype (2,4,8,12), 7 none (2,3,5,6,15,16,18). The success metric "drops from 7/7/5/6" therefore has the wrong baseline. Fix: re-tag and recount, then keep the corrected numbers in brief and spec.
13. **MINOR — Other unverified claims:** "Play's 2027 contact-picker policy: we qualify as core functionality" (spec §3); "fill Play's sensitive-permission declarations" for the notification listener (premortem #3; I know of no Play declaration form for `NotificationListenerService`, only an in-app disclosure/ policy review); "Android 15 hides OTP notifications from apps like ours" (true for listeners, but the brief should say other sensitive content is still visible). `references.md` is explicitly from memory, URLs not live-checked; do not quote it externally.

## E. Contradictions between brief, spec and premortem

23. **MAJOR — "Useful Today brief in under 60 seconds" (brief success metric) vs spec §5.** Spec step 4 says Today shows events immediately and the brief "appears when the model is ready", but the model download (379 MB and up) on patchy mobile data cannot finish in 60 s, and cold model load plus on-device generation is further seconds to a minute on low-end phones. Fix: define the metric as "first useful Today (events + facts list)" and make the facts list (not LLM prose) the primary content.
24. **MAJOR — Premortem #4 vs spec §2.1 / §2.2.** Premortem: "index/summarize only while charging or on explicit refresh". Spec: brief regenerates on open if older than 3 h, summaries are generated lazily for visible rows. Two conflicting rules; the safer reading kills the lazy summary design. Fix: one rule, stated once in the spec (e.g. brief on open is allowed when battery not low and heat guard ok; row summaries only on explicit action or charging).
25. **MAJOR — Premortem #3 "feature flag removable by a patch" vs #6 "Shorebird can't fix native".** The notification listener is a manifest `<service>` plus Kotlin; Shorebird patches Dart only. A Dart-side flag can hide the UI but the permission and service remain in the Play-reviewed binary. Premortem #3 also says "remote-free feature flag" but privacy.md promises "no feature flags that call out": it must be a compile-time flag. Fix: restate as "ship the listener in a separate Play track/flavor or accept a store release to remove it".
26. **MAJOR — Spec §2.2 "Add to calendar (confirm sheet)" vs §3 "read-only calendar" and §6 "writing calendar events directly" parked.** Either it is an `ACTION_INSERT` / iOS EventKitUI intent (needs no write permission; say so) or it contradicts the parking. Fix: specify as an insert-intent handoff.
27. **MAJOR — "Every sentence links to its source" (premortem #1, spec §2.1) vs "model writes 3-5 sentences of prose".** Free-form prose from a 0.5-1B model cannot be mapped sentence-to-source reliably. Fix: generate one sentence per fact from a template + model phrasing (one call per fact), or show the facts list as the tappable part and the prose as a header.
28. **MINOR — Brief says morning brief is "ready when you open the app, not after you type", spec generates on open (cold start + model load) and the morning notification is "optional".** What does the notification say if the model is not running at 7:00? Needs either exact alarms (`USE_EXACT_ALARM` / `SCHEDULE_EXACT_ALARM` are not in the manifest and are restricted on Android 14+), or an unattended generation which D16 says is unsupported.
29. **MINOR — Premortem #1 mitigation "eval set of 20 fixture days run in CI on a small model"** is not in spec §7's verification plan, and CI running a GGUF model is not stated as feasible.
30. **MINOR — Brief locked list says "Files/Notes folder"**; spec only supports a read-only folder index, no note creation (see 21, G7). Name drift: brief "Library — saved answers and to-dos", spec "Saved" and "Documents"; pick one.

## F. Workflow-first failures (dead ends, retyping, missing empty/error states)

31. **BLOCKER — 0.7a ships a shell whose main tabs have no content.** Phasing: 0.7a = new IA (Today, Inbox, Ask, Library) with no connectors; connectors land in 0.7b/0.7c. A 0.7a user (and every iOS user without Gmail, forever) gets a Today with no events, an Inbox with nothing to list, and a Library with no folder. Spec §2.1 only defines empty states for "no connectors" and "no model", and its CTA ("Connect your calendar") points to 0.7b functionality that does not exist yet. Fix: either gate tabs by availability (Inbox hidden until a mail/notification source is connected; 0.7a ships Ask + Actions + Library documents only) or move calendar to 0.7a. Reconcile with "never show a disabled feature" (premortem #10).
32. **MAJOR — Inbox, Library and Today have no error or offline states.** Missing: sync failed / offline (patchy data is the lead persona), mail returned HTML-only (spec caps "plain-text body", most mail is multipart/HTML; HTML to text is not specified), Gmail testing-token expiry shown inline with Reconnect, no model installed when summaries are requested, summary generation failed, Gmail "Save as draft" failing offline (the typed draft must be kept locally and offered Copy), empty Inbox ("Nothing needs a reply"), Library search no results, folder permission revoked or folder moved, scanned PDFs that yield no text (counted in "312 files indexed"?), files over size cap (skipped silently).
33. **MAJOR — Permission-denied dead ends repeat D15.** State machine: "cancel / denied (explain + retry)". On Android a twice-denied runtime permission cannot be re-prompted, so Retry does nothing; needs "Open Settings". Same for Calendar, Contacts, Notification listener (special access, "restricted settings" blocks sideloaded installs from enabling it until the user opts in) and iOS calendar (limited access).
34. **MAJOR — Ask "Sources" chips: pinning a source that is not connected, or that returned nothing, is unspecified.** User picks "Mail", Gmail not connected: answer from model memory presented as grounded? Fix: chip shows Connect, and zero-hit retrieval says "found nothing in Mail" instead of answering ungrounded.
35. **MAJOR — Notification rows and brief sentences about notifications have no destination.** "Each sentence opens its source": a notification source cannot be reopened (the original `PendingIntent` is not storable once dismissed). "Clear marks read" is ambiguous: marks in Dhruva, or dismisses the source notification (needs `cancelNotification`, a stronger action than the spec's "read only")? There is no "reply" path for chat-app notifications (Riley's WhatsApp step); Draft reply is mail-only.
36. **MAJOR — Cross-process write to the database.** Spec §3: the Kotlin `NotificationListenerService` writes "into the store" (the Drift DB). The service runs without the Flutter engine, with a different SQLite binding, while Dart may hold the file open; FTS5 virtual tables may not exist in the framework SQLite on minSdk 26. Fix: the service appends to a small queue file / its own table; Dart ingests on open.
37. **MAJOR — Revoke semantics.** "Revoke deletes tokens, local items, FTS rows" does not call Google's disconnect/revoke (grant remains in the user's Google account), and cannot revoke OS permissions for Calendar, Contacts or the notification listener (user must go to system Settings). State machine moves to NotConnected while the OS grant still exists, so the next open may silently resume. Fix: Revoke = local delete + "Open system settings to remove access" step + Google disconnect.
38. **MINOR — Settings reachable only from Today's gear.** From Ask, Inbox or Library it requires switching tab first; the "no model" error in Ask must deep-link to Models. Gear plus status pill plus date plus greeting on Today's header is also crowded (D10 repeat).
39. **MINOR — Contacts minimality vs priority rule.** "Contact known" as a priority signal requires matching every sender email against contacts; either read all contacts (violates "limited to people appearing in events/mail" in spirit) or query per sender. State which.
40. **MINOR — Onboarding step 2-3 data cost.** Model download starts "in background" before the user chooses Wi-Fi or mobile data; screens-map notes the existing flow blocks without explanation. Specify metered-network consent and a visible pause/resume.

## G. Risky assumptions not in the premortem

41. **MAJOR — Background execution.** WorkManager periodic sync assumes a Dart isolate can run Gmail (silent token), Calendar and Contacts plugins and write Drift; none of `workmanager`, `home_widget` or a local-notification plugin is in `pubspec.yaml` today (WorkManager is only present via `background_downloader`). 42. **MAJOR — `device_calendar_plus` is a 0.x package** (0.12.0). Maintenance and API-churn risk on the only no-sign-in first-run path (the entire onboarding promise). Add fallback (platform channel to `CalendarContract`, small).

Apple review also needs a Gmail demo account and justification for Contacts/Calendar strings; none of the Info.plist usage strings exist yet (`Info.plist` has only camera, microphone, photo library).
